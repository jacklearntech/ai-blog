# Jack 的 AI Blog

这是我的个人技术博客，主要记录 AI、软件工程和技术探索方面的内容。

整个站点用 [Next.js](https://nextjs.org/) + [Tailwind CSS v4](https://tailwindcss.com/) + [MDX](https://mdxjs.com/) 搭建，构建后是纯静态 HTML。

## 线上地址

同一份代码同时部署在两个地方，**两个地址内容一致**：

| 托管方           | 地址                              | 说明                                     |
| ---------------- | --------------------------------- | ---------------------------------------- |
| 阿里云轻量服务器 | https://www.jacklearn.tech        | 主站。Nginx 直接托管构建产物 `out/`      |
| Vercel           | https://blog.jacklearn.tech       | 关联本仓库，push 到 `main` 后自动部署    |

根域 https://jacklearn.tech 指向主站。

> 上面这张表只是给人看的摘要。**地址的真实来源是 `site.config.json`** —— 构建脚本、检查脚本
> 都从那里读，改地址只改那一处。文档里不再各自复述一份，否则改的时候必然漏一个
> （这个项目真的漏过一次，而且漏的那一处让 Vercel 上的 RSS 全变成了死链）。

## 订阅

站点提供 RSS 订阅源，地址是 `https://www.jacklearn.tech/rss.xml`。

在页面上找入口的话有两个地方：

- **首页标题右侧**有一个「RSS 订阅」按钮（橙色图标那个）
- **页脚**也放了一个同样的链接，所以文章页、标签页都能点

除了可见的按钮，每个页面的 `<head>` 里还写了
`<link rel="alternate" type="application/rss+xml">`。这一条是给阅读器用的：把站点地址直接粘进
Feedly、NetNewsWire 这类阅读器，它靠这个标签自动找到订阅源，不用你手动猜 `/rss.xml` 这个路径。

> RSS 不是页面，是构建时由 `scripts/generate-rss.ts` 写进 `out/rss.xml` 的文件，所以它没有对应的
> 路由源码 —— 想改内容只能改文章或改那个脚本，改完重新构建才会更新。

## 给搜索引擎的两个文件

- **`/robots.txt`** —— 内容只有「全部允许」，另外一行 `Sitemap:` 指向下面的清单。
  真正要挡的东西（扫描器、漏洞探测路径、空 UA）是在 nginx 层直接返回 444 的，**故意不写进这里**：
  robots.txt 是对善意爬虫的请求，不是访问控制，把黑名单写进去等于把规则告诉对手，对不遵守的人也无效。
- **`/sitemap.xml`** —— 全站页面清单：首页、标签索引、每篇文章、每个标签页。发新文章后条目会自动增加。

这两个都不是静态文件，而是构建期由 `src/app/robots.ts` 与 `src/app/sitemap.ts` 生成的 —— 要改只能改源码、
重新构建。之所以不放在一个 public 目录里，是因为那个目录名不在发布脚本的提交白名单里，放进去的文件会
在服务器上生效却永远推不到 GitHub，属于最难发现的一类问题。

## 本地跑起来

```bash
npm install        # 装依赖
npm run dev        # 启动开发服务器，访问 http://localhost:3000
npm run build      # 构建静态站点 + 生成 RSS + 校验产物路径
npm run check:docs # 校验文档里的域名/路径/脚本名与仓库实际是否一致
npm start          # 预览构建产物
```

## 怎么写文章

在 `content/` 目录下新建一个 `.mdx` 文件就行，**文件名就是文章的 URL slug**。文件开头用 YAML frontmatter 写元信息：

```mdx
---
title: "文章标题"
date: "2026-08-17"
summary: "首页列表里显示的简短描述"
tags: ["ai", "教程"]
---

正文内容写在这里，支持完整的 Markdown 语法，还能嵌入 React 组件...
```

### frontmatter 字段说明

| 字段      | 必填 | 说明                                                         |
| --------- | ---- | ------------------------------------------------------------ |
| `title`   | 是   | 文章标题                                                     |
| `date`    | 是   | 发布日期，格式 `YYYY-MM-DD`                                  |
| `summary` | 否   | 摘要，显示在首页文章列表里                                   |
| `tags`    | 否   | 标签数组，用于分类和导航                                     |

> ⚠️ `draft` 字段目前**不生效**。只有 RSS 生成脚本会跳过 `draft: true` 的文章，
> 但文章列表和 `/posts/<slug>` 依然会生成。想「藏稿」只能先别把文件放进 `content/`。

### 命名约定（重要）

静态导出的产物文件名直接由路由参数决定，命名踩坑不会报错，只会让页面 404，所以写成硬约定：

- **slug（文件名）必须纯 ASCII**，用 `-` 连接，例如 `my-first-post.mdx`。
  它是 `/posts/<slug>` 的唯一入口，中文文件名会得到一个很难排查的 404。
- **标签建议用 ASCII 单 token**（`Nginx`、`DevOps`），避免空格。带空格的标签虽然现在能正常访问，
  但会让 URL 变成 `%20` 形式，不太好分享。
- `title` / `summary` / 正文**随便用中文**，它们不参与文件名。
- 改代码时：**`generateStaticParams()` 必须返回标签原文**，`encodeURIComponent` 只能出现在
  链接的 `href` 里。前者决定磁盘上的文件名，后者决定链接长什么样 —— 这两个位置看起来很像，
  职责完全不同，把它俩搞混就是当初标签页 404 的根因。

构建末尾有一道守卫（`scripts/check-export-paths.ts`）会扫描产物，一旦发现文件名里出现 `%`
就**直接让构建失败**，从而避免这类问题被悄悄部署上线。这条守卫的存在理由很实际：纯 ASCII 的
路由编码前后完全一样，会把这个错误完美掩盖 —— 「检查全绿」和「部分链接 404」可以同时成立。

## 项目结构

```
content/          # MDX 文章放这里
src/app/          # Next.js 页面（App Router）
src/components/   # React 组件
src/lib/          # 工具函数（文章解析等）
scripts/          # 构建与检查脚本（RSS 生成、产物路径守卫、文档一致性检查）
ops/              # 部署脚本
.ai/              # 项目文档（架构、模块说明、决策记录）
site.config.json  # 站点地址的单一来源
```

## 部署

项目使用静态导出（`output: 'export'`），可以部署到任何支持静态文件的地方：

- **Vercel**：关联 GitHub 仓库后自动部署，push 即更新（配置见 `vercel.json`）
- **自建服务器**：Nginx 直接指向 `out/` 目录；`ops/release.sh` 封装了完整的构建与上线流程
- **其他静态托管**：把 `out/` 目录上传即可

> **部署前提**：托管方需要支持「无扩展名 URL → 对应的 `.html` 文件」这种映射。
> 纯静态模式下 Vercel 默认不开启，必须在 `vercel.json` 里打开 `cleanUrls`，
> 否则站内所有 `/posts/xxx`、`/tags` 这类链接都会 404 —— 症状很迷惑：首页正常打开，
> 但点任何一篇文章都挂。

### 环境变量

| 变量       | 必填 | 说明                                                     |
| ---------- | ---- | -------------------------------------------------------- |
| `SITE_URL` | 否   | 覆盖 RSS 里的绝对地址。**正常情况下不用设**，不设时会读 `site.config.json` 的 `canonicalOrigin` |

> 这里曾经写死过一个兜底的域名。那个域名后来被废弃、整站 404，而 Vercel 的构建环境里没有
> `SITE_URL`，于是兜底值生效 —— Vercel 上的 `/rss.xml` 里每一条链接都指向一个打不开的站。
> 站点本身完全正常，所以没有任何症状。现在读不到地址会**直接让构建失败**，宁可报错也不猜。

## 文档与事实的一致性

这个项目踩过的最典型的坑，是「同一个事实被写在好几个地方，改的时候只改了其中一部分」。

所以现在有一条约定：**站点地址只写在 `site.config.json` 里**，其它地方一律引用、不复述；
`npm run check:docs` 会把文档里的断言当成可机器校验的对象 —— 域名是否登记过、反引号里的文件
路径是否真的存在、提到的 npm 脚本是否真的在 `package.json` 里。发布流程（`ops/release.sh
publish`）在提交之前会自动跑一遍，不通过就不发布。

注意它只保证「文档没有说错站点是什么」，保证不了「文档说的都对」。真正的判断还是得靠人。
